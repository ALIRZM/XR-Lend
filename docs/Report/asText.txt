TASK 1
1.1 The Problem
University XR labs hold a small number of expensive headsets that many students need to share. Most labs still run this on a paper sign-out sheet, a whiteboard, or a shared spreadsheet.
This causes four problems:
1.	Double bookings. Two students book the same headset for overlapping days because nobody can see the full calendar at once.
2.	No record of who has what. When a headset goes missing, staff cannot say who had it last or when it was due back.
3.	Students waste trips. A student walks to the lab to find every headset is already out, because availability is not visible before they leave.
4.	Damage is untracked. A headset comes back with a cracked lens and there is no record linking that damage to a specific loan.
The lab technician ends up doing the scheduling by hand and holding the whole picture in their head.
XRLend fixes this. It is one website where the technician keeps the headset list up to date, students see what is actually free for the dates they want, and every loan is recorded from request through to return.
Why this is worth building. The main problem is a scheduling rule, it's not a data entry form. Two loans of the same headset must not overlap in time. That single rule is what a spreadsheet cannot do and what the system can support.

1.3 User Roles

Can do	Student	Technician
Sign up and log in	Yes	Yes
Browse the headset list	Yes	Yes
Check availability for a date range	Yes	Yes
Request a loan	Yes	No
Cancel own pending request	Yes	No
See own loan history	Yes	No
Add, edit or retire a headset	No	Yes
Set a headset to under maintenance	No	Yes
Approve or reject a request	No	Yes

Students can request a headset. Only the technician can approve it and hand it over. This matches how equipment loans normally work, and fewer rules means fewer things to test.
1.4 The Two End-to-End Workflows
Each workflow belongs to a different role and finishes on its own. They meet at the loan request, which is what makes this one system rather than two

Workflow A — Borrow a headset (Student)
Step	What happens	Requirement
A1	Student logs in	R2
A2	Browses headsets and enters the dates they want	R4
A3	System shows which headsets are free for those dates	R5
A4	Student requests a loan for one of them	R6
A5	Request sits as Pending until the technician decides	R6
A6	Student sees the decision on their loan list, with the reason if it was rejected	R7
Finished when: the request has been approved or rejected and the student can see which.
Workflow B — Manage the lab (Technician)
Step	What happens	Requirement
B1	Technician logs in	R2
B2	Adds a headset with its model and asset tag	R3
B3	Headset is saved as Available and students can now find it	R3
B4	Technician opens the pending request queue	R8
B5	Checks the dates and approves or rejects, giving a reason if rejected	R9
B6	Queue updates and the student sees the decision	R9
Finished when: the request has a decision recorded against it and the queue no longer shows it.
1.5 Scope
In scope
•	Sign up, log in, log out
•	Two roles, chosen at sign up, with a staff code required for the technician role.
•	Headset records with model, asset tag, status and notes
•	Availability search across a date range
•	Loan requests with start and end dates
•	Approve and reject steps, with a reason on rejection 
•	Recording collection and return, built after the two workflows
•	Overlap checking so one headset cannot be double booked
•	Student loan history
•	Technician view of all loans
•	Input checks on all forms
•	Manual deployment to AWS EC2 with written steps
Out of scope
Left out	Why
Payments, fines or deposits	Brings in payment security rules, too big for this unit
Email or SMS alerts	Needs an external mail service and adds a dependency we do not need to show the workflow
University single sign-on	Normal login is enough and keeps the system self-contained
Barcode or QR scanning	Needs hardware we do not have. The asset tag is typed in
Mobile apps	A responsive website is enough
Booking rooms or desks as well	Headsets only. Adding more equipment types would widen the model without adding new reasoning
Waiting lists	If nothing is free the student picks other dates. A queue adds a lot of rules for little value here
Usage reports and charts	Counting loans is enough. Charts do not test any new rule
Automatic CI/CD	The brief says this is out of scope
Assumptions
1.	One AWS region (ap-southeast-2) and one EC2 instance, same as Tutorial 4.
2.	Data is stored in MongoDB Atlas, same as Tutorial 4.
3.	The lab holds 30 headsets, so availability can be checked without heavy optimisation.
4.	Loans are whole days. There are no hourly bookings.
5.	Collection and return happen in person, so the system records them but does not control them.
6.	One technician is on duty at a time, so two staff will not approve the same request at once.
7.	The team is 1 person working about 15 hours a week.
8.	The site only needs to be running during the marking period.
9.	AWS free tier is enough for a demo with a few users.
10.	The lab holds a single staff access code, given out in person by the lab manager. There is no per-person staff invite.

•	Given no token, when a protected route is called, then the server returns 401.
•	Given a technician token, when it is sent to a technician route, then the request goes through.

Story 1.5 — Unit tests to 70% coverage  · 5 pts · Must · Task

Epic 3 — Availability and Requests · 24 points · Needs Epic 2
All of Workflow A. This is where the overlap rule is enforced for the first time.
Story 3.1 — Browse the headset list  · 3 pts · Must · R3
As a student, I want to see what headsets exist, so that I know what I can ask for.
Acceptance criteria
•	Given I am logged in as a student, when I open the list, then I see model, asset tag and status.
•	Given there are no headsets, when I open the list, then I see a message, not a blank page.
Story 3.2 — Search availability for a date range  · 8 pts · Must · R3, R6
As a student, I want to enter my dates and see only what is free, so that I do not ask for something already booked.
Acceptance criteria
•	Given a start and end date, when I search, then only headsets with no Pending or Approved loan overlapping those dates are shown.
•	Given an end date before the start date, when I search, then I see a validation message and nothing is sent.
•	Given nothing is free, when I search, then I see a message suggesting other dates.
Sub-tasks
•	Overlap query, availability route, date picker, seven boundary tests.
The seven overlap tests
An existing loan runs day 10 to day 14. A new request must be refused for 8 to 12, 12 to 14, 14 to 18, 8 to 18 and 10 to 15. It must be allowed for 5 to 9 and for 16 to 20.
Story 3.3 — Request a loan  · 8 pts · Must · R4, R6
As a student, I want to request a headset for my dates, so that the technician can decide.
Acceptance criteria
•	Given a free headset and valid dates, when I submit, then a loan is created with the status Pending.
•	Given someone booked the same dates while I was filling in the form, when I submit, then my request is refused with a message saying it is no longer free.
•	Given I am a technician, when I call the request route, then the server returns 403.
Sub-tasks
•	Loan model, POST route, second overlap check before save, request form.
Story 3.4 — See my loans and cancel a pending request  · 5 pts · Must · R4
As a student, I want to see my requests and drop one I no longer need, so that I know where I stand and do not hold dates I will not use.
Acceptance criteria
•	Given I have loans, when I open my loans, then I see each one with its dates and status, newest first.
•	Given a request was rejected, when I open my loans, then I can see the reason.
•	Given a Pending request, when I cancel it, then its status becomes Cancelled and those dates are free again straight away.
•	Given an Approved loan, when I open it, then there is no cancel button.
Epic 4 — Approvals and Returns · 18 points · Needs Epic 3
The rest of Workflow B. The decision is where the overlap rule is checked for the last time.
Story 4.1 — See the pending request queue  · 5 pts · Must · R5
As a technician, I want one list of everything waiting, so that nothing sits unanswered.
Acceptance criteria
•	Given there are pending requests, when I open the queue, then I see student, headset and dates, oldest first.
•	Given the queue is empty, when I open it, then I see a message, not a blank page.
•	Given I am a student, when I call the queue route, then the server returns 403.
Story 4.2 — Approve or reject a request  · 8 pts · Must · R5, R6
As a technician, I want to decide on a request, so that the student knows where they stand.
Acceptance criteria
•	Given a pending request with no clash, when I approve it, then its status becomes Approved and the student can see it.
•	Given a clash appeared since the request was made, when I approve it, then it is refused and the status stays Pending.
•	Given I reject a request, when I save, then a reason is required and the student can see it.
Sub-tasks
•	Approve route, reject route with reason, second overlap check inside approve, clash test.
Story 4.3 — Record collection and return  · 5 pts · Should · R5
As a technician, I want to record the handover and the return, so that the lab knows who has what.
Acceptance criteria
•	Given an approved loan, when I record collection, then the status becomes Collected with a timestamp.
•	Given a collected loan, when I record the return, then the status becomes Returned and I can mark the condition as Good or Damaged.
•	Given a returned loan, when a student searches those dates, then the headset is free again.
